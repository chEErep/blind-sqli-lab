# Blind SQLi Lab

Учебный стенд для отработки time-based blind SQL injection на небольшом веб-приложении.

Суть простая: есть форма восстановления пароля, которая в уязвимом режиме собирает SQL-запрос небезопасно. Из-за этого можно через задержки (`SLEEP`) побуквенно вытянуть `reset_token` пользователя, сбросить ему пароль и зайти под его аккаунтом.

## Что внутри

- `backend/` — Flask-приложение (логин, регистрация, восстановление пароля, личный кабинет)
- `db/init.sql` — схема БД и тестовые пользователи
- `docker-compose.yml` — подъём MySQL + backend
- `exfil.py` — скрипт для автоматической эксфильтрации токена по таймингу
- `ИНСТРУКЦИЯ*.md` — заметки по ручной проверке через Burp и sqlmap

## Как запустить

Нужен Docker Desktop.

> В `docker-compose.yml` папка `../music` монтируется в контейнер для плейлистов на дашборде. Если этой папки нет, можно создать пустую `D:\Практика\music` рядом с проектом или закомментировать строку с volume в compose.

```bash
docker compose up --build
```

После запуска:

- приложение: http://localhost:8000
- проверка состояния: http://localhost:8000/health

Остановить и удалить данные БД:

```bash
docker compose down -v
```

## Тестовые аккаунты

| Логин | Пароль | Комментарий |
|---|---|---|
| `alice` | `alice123` | обычный пользователь |
| `administrator` | неизвестен | цель для демонстрации угона |

У `administrator` в `init.sql` заранее задан `reset_token`, чтобы можно было быстро проверить цепочку эксплуатации.

## Где уязвимость

Уязвимый endpoint — `POST /forgot`. В файле `backend/app.py` есть два варианта обработки email:

- `find_user_by_email_safe()` — параметризованный запрос
- `find_user_by_email_vulnerable()` — конкатенация строки в SQL

Режим переключается переменной окружения `SAFE_MODE` в `docker-compose.yml`.

Сейчас в compose по умолчанию стоит `SAFE_MODE: "false"`, то есть стенд запускается в уязвимом режиме.

## Как воспроизвести вручную

1. Открыть форму "Забыли пароль?".
2. Отправить payload в поле `email` и смотреть на время ответа.

Проверка, что инъекция вообще есть:

```text
x' OR (SELECT SLEEP(5))-- -
```

Проверка булевой логики через время:

```text
x' OR (SELECT CASE WHEN (1=1) THEN SLEEP(5) ELSE 0 END)-- -
x' OR (SELECT CASE WHEN (1=2) THEN SLEEP(5) ELSE 0 END)-- -
```

Дальше можно посимвольно вытаскивать `reset_token` из таблицы `users` и использовать его на `/reset?token=...`.

## Автоматизация

В репозитории есть скрипт `exfil.py`. Он сам меряет базовое время ответа, определяет длину токена и подбирает символы.

```bash
python exfil.py http://localhost:8000
```

## Почему это работает

Проблема в том, что пользовательский ввод попадает прямо в SQL-запрос. Даже если страница не показывает результат запроса, атакующий может получать информацию по косвенному каналу — времени ответа сервера.

В этой лабе цель не "достать пароль из БД", а получить токен сброса. Пароли хранятся хэшем, а валидный `reset_token` позволяет сменить пароль и захватить аккаунт.

## Как защищаться

- Использовать параметризованные запросы, а не строковую конкатенацию.
- Не строить SQL из пользовательского ввода вручную.
- Ограничивать частоту запросов на чувствительные endpoint'ы.
- Логировать подозрительные запросы и ставить алерты.
- Выдавать токены сброса на короткий срок и делать их одноразовыми.
